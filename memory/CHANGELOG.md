## 2026-06 (fork) — BUGFIX: bulk music upload failing at scale (15/9 work, 40/large fail)
- Root cause: the whole bulk upload ran as ONE synchronous request that streamed every file to disk + did a BLOCKING Tigris S3 PUT per file. Total time scales with payload; on real upload bandwidth a large batch (hundreds of MB) exceeds the platform ingress request timeout mid-transfer → the client sees "upload failed" (backend often keeps going, so partial tracks land). Reproduced: 40×8MB (335MB) took ~50s in-datacenter — real users on normal uplinks cross the timeout well before that. Concurrency gate and app limits (200 files / 5GB) were NOT the cause. Missing ffmpeg was a red herring (mutagen already provides duration; `_ffprobe_duration` is a safe fallback).
- Fix (frontend `AdminBulkUpload.jsx`): client-side CHUNKING — staged files are split into small requests (≤12 files AND ≤30MB each), uploaded sequentially, and every batch's result aggregated into one summary. Added a live "Uploading batch X of N…" progress indicator. Each request now stays comfortably under the ingress timeout regardless of batch size or user bandwidth.
- Fix (backend `admin_tracks_bulk.py`): offloaded the blocking Tigris `upload_bytes` to `asyncio.to_thread` so it no longer stalls the event loop during a bulk request.
- Also restored ffmpeg/ffprobe (dropped from the pod again — benign for uploads but used by radio/BGM).
- Verified: browser e2e uploaded 25 files → 3 batches → "Uploaded 25 tracks", 25 rows, no console errors. Backend single-batch still 200 OK after the thread-offload.
