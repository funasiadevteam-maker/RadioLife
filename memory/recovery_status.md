# BigFM — Track Catalog Recovery Status (2026-06-07)

## Critical finding — the rescued catalog is NOT real music

The 485 "orphan" .mp3 files found on `/app/backend/storage/tracks/` and
registered as active tracks in the prior hotfix turn out to be **test
fixtures**, not real audio.  Sample inspection confirms:

- All 499 files are **<30 seconds long** (most are ~1,690 bytes — silent
  or near-silent MP3 stubs created by the bulk-upload tests in
  `tests/test_phase22a_bulk_upload.py`, `tests/test_phase22c_*.py`, etc.).
- Their titles are placeholder strings like `zip_x_976198`,
  `p22g_ok_0a3f12`, `loose_a_4d2e91` — these are generated by the
  pytest fixtures.
- ID3 tags are missing; mutagen extraction yielded "Unknown Artist"
  for every file.

This is why the listener perceives "just RJ" — the radio engine IS
selecting and serving these tracks (curl proves audio/mpeg bytes flow),
but each song slot is 2–3 seconds of silence between 15–25-second RJ
segments.  From the user's ear, it sounds like wall-to-wall RJ.

**Action required (user, manual)**: Re-upload real music via
`POST /api/admin/tracks/bulk-upload` (the bulk-upload UI at
`/admin/tracks/bulk-upload`).  The Phase 22e-stream refactor + dedupe
addendum will handle large zips cleanly once it ships.

## The 137 hard-deleted broken_storage_missing rows

These rows referenced `s3://bigfm-storage/tracks/<uuid>.mp3` keys that
returned **HTTP 404** from Tigris (the bucket simply doesn't have those
objects), and had no local file fallback.

**Recovery status**: **UNRECOVERABLE from any source**.

Sources checked:
- `/app/backend/storage/tracks/` — no matching UUIDs.
- `/app/backend/storage/tracks_backup/` — directory does not exist.
- `/tmp/*tracks*` — no candidates.
- Tigris bucket via signed-URL probe (5-second timeout each) — every key
  returned 404.

What we still know about them: the Mongo `_id` for each was logged in
the `delete` pass of `rescue_orphan_tracks_and_purge_broken.py`
(stdout captured in commit 83 message + supervisor logs).  Titles in
that log include strings like `Tadak Tadak{iSHAT @KKlive...}` etc. —
genuine song names from a previous upload session that's lost.

**User recourse**: re-upload from the original library via the bulk
upload UI.  The new dedupe addendum (Phase 22e-stream session) will
correctly handle re-uploads — files matching existing rows by ISRC or
hash will be skipped with an audit log entry; net-new content will be
imported normally.
